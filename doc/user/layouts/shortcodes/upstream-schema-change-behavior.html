{{- /* Describes how a Materialize source behaves when the upstream table undergoes schema changes or destructive operations. Single source of truth shared by the Postgres, MySQL, and SQL Server ingestion pages. Takes a `connector` param (`postgres`, `mysql`, or `sql-server`). Source- versioning links are built from the connector so each page links to its own guide. Postgres-only concepts (publications, replica identity, exclusion constraints) render only when connector == "postgres". Call with the `{{% %}}` form so the inner markdown renders: {{% upstream-schema-change-behavior connector="postgres" %}} */ -}} {{- $connector := .Get "connector" -}} {{- $is_postgres := eq $connector "postgres" -}} This section describes how changes to upstream tables that Materialize ingests affect the corresponding Materialize tables. ### Adding a column When you add a new column to your upstream table, Materialize continues to ingest only the existing columns. To incorporate the new column: - If using the new [`CREATE SOURCE` and `CREATE TABLE FROM SOURCE`](/sql/create-source/{{ $connector }}-v2/) syntax, create a new table from the source. See [Handle upstream column addition](/ingest-data/{{ $connector }}/source-versioning/#handle-upstream-column-addition). - If using the legacy [`CREATE SOURCE ... FOR ...`](/sql/create-source/{{ $connector }}/) syntax that creates subsources, use [`DROP SOURCE`](/sql/drop-source/) to drop the affected subsource, and then add the table back to the source using [`ALTER SOURCE ... ADD SUBSOURCE`](/sql/alter-source/). The re-added subsource includes the new column. ### Dropping a column Dropping columns that Materialize does not ingest (for example, columns added after the source was created, or columns that are excluded) is supported. As these columns were never ingested, you can drop them without issue. If your Materialize source ingests a column, dropping that column from your upstream table puts the affected table into an error state. {{ if eq $connector "sql-server" }} Adding a column with the same name back does not undo this. The capture instance keeps its original column and receives `NULL` for it from then on, so Materialize treats the recreated column as dropped. {{ end }} - If using the new [`CREATE SOURCE` and `CREATE TABLE FROM SOURCE`](/sql/create-source/{{ $connector }}-v2/) syntax, you can safely drop a column by first ignoring it in Materialize. See [Handle upstream column drop](/ingest-data/{{ $connector }}/source-versioning/#handle-upstream-column-drop). - If using legacy [`CREATE SOURCE ... FOR ...`](/sql/create-source/{{ $connector }}/) syntax, use [`DROP SOURCE`](/sql/drop-source/) to drop the affected subsource, and then add the table back to the source using [`ALTER SOURCE ... ADD SUBSOURCE`](/sql/alter-source/). ### Changing constraints Materialize records some upstream constraints when a table is created and ignores the rest. Only recorded constraints matter afterwards. Adding any constraint upstream is a non-event. Dropping an ignored constraint is a non-event. Dropping a recorded constraint puts the affected table into an error state that names the constraint. Constraints added after the Materialize table was created are never recorded, so adding one and later dropping it does not affect ingestion. {{ if $is_postgres -}} | Upstream constraint | Recorded as | Dropping it upstream | |---|---|---| | `PRIMARY KEY` | A key. Its columns are also non-nullable. | Error state. | | `UNIQUE` constraint | A key, which the optimizer can use when every column is `NOT NULL` or the constraint is `NULLS NOT DISTINCT`. | Error state, even when the key was not usable. | | Unique index created with `CREATE UNIQUE INDEX`, including partial and expression indexes | Not recorded. | Non-event. | | `NOT NULL` | The column's nullability. | Error state. | | `CHECK`, `FOREIGN KEY`, `EXCLUDE`, `DEFAULT` | Not recorded. | Non-event. | Materialize compares the upstream catalog against the recorded schema every few seconds and whenever the replication stream announces a table change, so a dropped constraint is reported within seconds. {{ else if eq $connector "mysql" -}} | Upstream constraint | Recorded as | Dropping it upstream | |---|---|---| | `PRIMARY KEY`, the index named `PRIMARY` | A key. | Error state. | | Unique index over columns, including prefix indexes such as `UNIQUE (name(10))` and `INVISIBLE` indexes | A key, which the optimizer can use when every column is `NOT NULL`. | Error state, even when the key was not usable. Changing an index's visibility is a non-event. | | Unique index over an expression | Not recorded. | Non-event. | | Non-unique `INDEX`, `FULLTEXT`, `SPATIAL` | Not recorded. | Non-event. | | `NOT NULL` | The column's nullability. | Error state. | | `CHECK`, `FOREIGN KEY` | Not recorded. | Non-event. | Materialize checks the upstream schema when the DDL statement appears in the binlog, so a dropped constraint is reported as soon as it replicates. {{ else -}} | Upstream constraint | Recorded as | Dropping it upstream | |---|---|---| | `PRIMARY KEY` | A key. Its columns are also non-nullable. | Refused by SQL Server: the capture instance is bound to the primary key's index, and SQL Server does not allow dropping or disabling that index while the capture instance exists. | | `UNIQUE` constraint | A key. | Error state, unless the constraint is the index the capture instance was bound to, which SQL Server refuses to drop. | | Unique index created with `CREATE UNIQUE INDEX` | Not recorded. | Non-event. | | `NOT NULL` | The column's nullability. | Error state. | | `CHECK`, `FOREIGN KEY`, `DEFAULT` | Not recorded. | Non-event. | SQL Server does not record constraint changes in `cdc.ddl_history`, so Materialize re-reads each table's definition on every poll that finds new changes and compares it against the recorded schema. Dropping a constraint writes to the log, so a dropped constraint is reported within seconds. Excluding the primary key with `EXCLUDE CONSTRAINTS` is allowed but raises a `NOTICE`: it removes the key from the Materialize table, but it cannot make an upstream drop a non-event, because SQL Server refuses that drop anyway. {{ end }} To drop a recorded constraint without interrupting ingestion, recreate the Materialize table with the constraint excluded before the upstream drop, using `EXCLUDE CONSTRAINTS` for a named `PRIMARY KEY` or `UNIQUE` constraint, or `EXCLUDE ALL CONSTRAINTS`, which also covers `NOT NULL`. ### Changing a column's data type {{ if $is_postgres -}} Changing an ingested column's data type upstream puts the affected Materialize table into an error state unless the column was ingested as `text` via the `TEXT COLUMNS` option. Ingestion for that table stops, and you must drop and recreate the table in Materialize to resume ingestion. {{ else if eq $connector "mysql" -}} Changing an ingested column's data type upstream so that it maps to a different Materialize type than before puts the affected Materialize table into an error state. Ingestion for that table stops, and you must drop and recreate the table in Materialize to resume ingestion. Changing an ingested column's upstream data type so that it continues to map to the same Materialize type does not interrupt ingestion. For example, changing `tinyint` to `smallint`, changing within the `text`/`tinytext`/`mediumtext`/`longtext` family, and adjusting `bit(n)` precision are all safe. Appending new values to the **end** of an existing enum does not put the table into an error state. However, the newly-added values are not recognized, so rows that use them fail to decode until you drop and recreate the table. Existing enum values remain recognized, and rows that use them continue to decode successfully. Any other enum change puts the affected Materialize table into an error state, including inserting a value before the end, reordering or renaming values, and removing values. {{ else if eq $connector "sql-server" -}} Changing an ingested column's data type upstream puts the affected Materialize table into an error state, unless the column was ingested as `text` via the `TEXT COLUMNS` option and the new type is read the same way, for example a `decimal` precision or scale change. Widening a bounded type such as `varchar(10)` to `varchar(20)` is a type change. Ingestion for that table stops, and you must drop and recreate the table in Materialize to resume ingestion. Other `ALTER COLUMN` changes that keep the column's type and nullability, such as its collation, do not affect ingestion. Adding `NOT NULL` does not affect ingestion either. Dropping `NOT NULL` is covered under [Changing constraints](#changing-constraints). {{ end }} ### Renaming a column Renaming a column that Materialize ingests puts the affected table into an error state. Ingestion for that table stops, and you must drop and recreate the table in Materialize to resume ingestion. {{ if eq $connector "sql-server" -}} ### Removing a capture instance SQL Server allows up to two capture instances to exist for a table at once. Materialize ingests from one of them. Removing the capture instance that Materialize is using puts the affected table into an error state. Removing a capture instance that Materialize is not using does not affect ingestion. {{ end -}} ### Table-level operations The following upstream operations put the affected table into an error state. Ingestion for that table stops, and you must drop and recreate the affected table in Materialize to resume: - Dropping a table (`DROP TABLE`){{ if $is_postgres }}, removing it from the publication (`ALTER PUBLICATION ... DROP TABLE`), or dropping the publication (`DROP PUBLICATION`){{ end }}. - Renaming a table or moving it to a different schema. {{ if $is_postgres }}- Setting a table's replica identity to anything other than `FULL` (`ALTER TABLE ... REPLICA IDENTITY`). {{ end }}{{ if ne $connector "sql-server" }}- Truncating a table (`TRUNCATE`). To clear a table without putting it into an error state, use an unqualified `DELETE FROM t;` instead. {{ end }}
